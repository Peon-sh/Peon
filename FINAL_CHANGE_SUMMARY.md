Technical reference for reviewing branch `teapot-impoved`. Written so another

## Architecture change in one line

AWS moves from *required dependency* to *optional provider*, and the machine Peon
runs on becomes a first-class deployment target — without changing how existing
installations behave.

```
BEFORE                                  AFTER
  AWS SQS ─── required                    Queue:   Postgres │ SQS
  S3 ─────── optional                     Storage: Local    │ S3
  SES ────── optional                     Email:   SMTP     │ Test │ SES
  SSH ────── only transport               Execution: Local  │ SSH
```

## Prisma migrations

Three, all additive. No data migration, no backfill, no destructive statement.

| Migration | Adds |
|---|---|
| `20260727120000_postgres_queue` | `QueueJob` table, `QueueJobStatus` enum, partial claim index |
| `20260727130000_server_execution_mode` | `ServerExecutionMode` enum, `Server.executionMode` defaulting to `REMOTE` |
| `20260727140000_setup_token` | `SetupToken` table |

Every existing `Server` row becomes `REMOTE`, which is exactly its prior
behaviour. **Both queue and executionMode migrations were hand-written, not
generated by Prisma** — verify with `prisma migrate diff` (T-MIG-003).

## Providers

Each resolver imports only the selected implementation, so the SQS path never
loads Prisma, the Postgres path never loads the AWS SDK, and SMTP never loads
nodemailer.

```
src/lib/queue/     types.ts  index.ts  providers/{sqs,postgres}.ts
src/lib/storage/   types.ts  index.ts  providers/{local,s3}.ts
src/lib/email/     types.ts  factory.ts  drivers/{test,smtp,ses}.ts
src/lib/executor/  types.ts  index.ts  {ssh,local}.ts
```

`src/lib/queue/sqs.ts` is now a re-export shim so all 11 original import sites
were left untouched.

## Queue

`SELECT … FOR UPDATE SKIP LOCKED` inside a single `UPDATE`, so concurrent workers
cannot claim the same row. No Redis, no new dependency.

**Claiming leases rather than deletes.** The row stays, `visibleAt` moves forward
by the lease (900s), status becomes `PROCESSING`. A dead worker never
acknowledges, the lease expires, another worker takes it — so a job cannot remain
`PROCESSING` forever. Trade-off: at-least-once delivery, matching the SQS
visibility-timeout semantics handlers were already written against.

Adds what SQS did server-side: `attempts` with `maxAttempts`, exponential backoff
capped at 300s, terminal `FAILED`, malformed-payload rejection. Preserves
drop-on-`NotFoundError`.

`purgeCompleted()` exists but **nothing schedules it** — completed rows accumulate.

## Executor abstraction

```
BEFORE   deployment logic → sshPool
AFTER    deployment logic → ServerExecutor ─┬─ SshServerExecutor → sshPool
                                            └─ LocalServerExecutor → /bin/sh
```

64 call sites across 10 files migrated in five groups, `deploy/engine.ts` last.
The engine never learns which transport it holds; no `if (executionMode)` was
added inside it. Verified by diff inspection: every changed line is an import, a
parameter type, or a call receiver.

Two deliberate transport branches, both contained:

1. **Reachability** (`assertReachable`) — remote pings SSH and drops the pooled
   session; local checks the Docker daemon.
2. **Provisioning** — a LOCAL server never runs `apt-get`/`systemctl` from the
   worker, and the OS allow-list is skipped, because that gate exists to guard
   package provisioning Peon will not attempt on its own host.

`LocalServerExecutor` shells out to the `docker` CLI rather than using dockerode,
so the engine's existing command strings are reused verbatim and there is one
code path.

## Local server

`Server.executionMode = LOCAL`. An ordinary row — same workspace scoping, RBAC,
destinations, settings, tags. `ip` is the literal string `local`, deliberately
not `127.0.0.1`, because a loopback address would imply an SSH hop.

Created by `ensureLocalServer()` (idempotent), called from `/api/setup` and
`/api/auth/onboarding`. Defaults `concurrentBuilds` to 1.

**Hybrid needs no extra work** — local vs remote is a per-server property, so one
workspace holds both and each service picks its target as before.

## Installer

`install.sh` — preflight (root, distro, arch, RAM, disk, ports), Docker and git
install, data directories, secret generation under `umask 077`, stack start with
`--wait`, one-time admin link.

**Idempotent:** an existing `.env` is never regenerated, because a fresh
`ENCRYPTION_KEY` would destroy an existing installation's data.

### Bootstrap

`SetupToken`: 32 random bytes, SHA-256 hash stored, 24h expiry, single use via
conditional `updateMany`, **refused once any user exists** so a leaked token
cannot mint a second admin. No default credentials anywhere. Page at
`/setup/[token]`, API at `/api/setup`.

## TLS

One gateway per machine owns :80/:443; the control plane is routed *through* it
as another labelled container on the shared `peon` network — the same mechanism
as a deployed app, not a special case. `docker-compose.gateway.yml` stops
publishing 3000 publicly, binds it to loopback, and adds Traefik and Caddy
labels. The `peon` network is declared external so the overlay joins the existing
gateway rather than creating a rival.

## Backups

`base64 <file>` over SSH into a Node Buffer held ~2.4× the dump size in heap; a
2 GB database needed ~5 GB and killed the worker. Now SFTP to a temp file, then a
streamed multipart upload — peak memory is one 8 MiB part. **New cost: disk equal
to the dump size.**

## Encryption

Two key modes, both permanent:

- **strict** — decodes to exactly 32 bytes, used directly.
- **legacy-derived** — anything else, SHA-256'd, as before.

Legacy support is permanent, not deprecated-with-removal: any future removal
destroys data for anyone who has not rotated.

Acceptability is decided by `lib/crypto/preflight.ts`, which is async and can
query the database — the env schema cannot, which is why format validation was
removed from it:

| Key | Fresh DB (0 users) | Existing DB |
|---|---|---|
| strict | start | start |
| placeholder / legacy | **refuse** | start + warn |

Ties go to "existing": an unreachable database warns rather than refusing.

Rotation via `ENCRYPTION_KEY_PREVIOUS` fallback plus `pnpm encryption:rotate`
across 17 columns in 13 models. A value decryptable by neither key is left
untouched, never overwritten.

## Security changes

Two live defects fixed:

1. **`isRegistrationEnabled` was never enforced** — stored, editable in the admin
   UI, read nowhere. Both vectors closed: email signup and Google
   auto-provisioning. Still permits the first user and pending invitees.
2. **`ENCRYPTION_KEY` accepted any string**, SHA-256-ing it into a guessable key.

Plus: local storage behind a session with path-traversal guards, Docker socket
restricted to the worker and asserted in CI, hashed single-use bootstrap token.

Full review: [docs/security-review.md](docs/security-review.md).

## Breaking changes

| Change | Impact |
|---|---|
| `docker compose --profile db up -d` | Now `docker compose up -d postgres` |
| Root compose starts app+worker by default | Previously required `--profile full` |
| `pnpm-lock.yaml` is stale | `pnpm install --frozen-lockfile` fails until regenerated |
| Web image runs migrations via a new `migrate` service | Ordering changed |

**Not breaking:** SQS, S3, SES, SSH servers, encryption keys, every existing env
variable.

## Upgrade concerns

1. **Run `pnpm install`** and commit the lockfile before anything else.
2. **Legacy `ENCRYPTION_KEY` holders need do nothing.** Upgrading keeps the data
   readable; a deprecation banner appears. Do **not** generate a new key without
   rotating — that destroys every stored secret.
3. Verify every `Server` row is `REMOTE` after migration.
4. Confirm `QUEUE_DRIVER` resolves to `sqs` if you use SQS (worker logs it).
